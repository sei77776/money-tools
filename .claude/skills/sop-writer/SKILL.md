# SOP Writer

An SOP is successful when a competent newcomer completes the task correctly
without asking a question. That is the bar; write to it.

## Step 1 — Interview the process owner

Ask one question at a time, not a list:

1. What triggers this process, and how do you find out it needs doing?
2. Walk me through it as you actually do it — not the idealized version.
3. Where do you go, log in, or click? Which systems, which accounts?
4. What decisions do you make along the way, and on what basis?
5. What goes wrong, how do you notice, and how do you fix it?
6. How do you know you're done and it worked?
7. Who do you escalate to, and when?

Press specifically on steps described as "then you just..." — that phrase almost
always conceals tacit knowledge, and it is where handovers break.

## Step 2 — Write it

Structure:

- **Purpose** — one sentence on why this exists.
- **Scope** — when this applies and, importantly, when it does not.
- **Owner and escalation contact.**
- **Frequency / trigger.**
- **Prerequisites** — access, credentials, tools, information needed before starting.
- **Steps** — numbered, imperative, one action each.
- **Decision points** — as a table: condition → action.
- **Definition of done** — an observable check, not a feeling.
- **Common problems** — symptom → cause → fix.
- **Revision history.**

Writing rules:
- Imperative voice: "Open the billing dashboard", not "the billing dashboard should be opened".
- One action per step. If a step contains "and", split it.
- Name exact things: exact menu labels, exact file paths, exact field names.
- Never write "as appropriate", "as needed", or "use your judgment" without stating the criteria that inform that judgment.
- Include a screenshot or link where a location is hard to describe in words.

## Step 3 — Set the review cadence

Every SOP has an owner and a review date. An SOP that silently goes stale is
worse than none, because people follow it. Put both in the header.

## Step 4 — Verify by testing

The verification step is not proofreading — it is a dry run:

1. Have someone who has never done the task follow the SOP verbatim.
2. Record every point where they stop, ask, or guess. Each one is a defect.
3. Fix and repeat.

If a live test is impossible, do a desk check: walk the steps yourself against
the real system and confirm each named element exists as written. Report which
form of verification you actually performed — never imply a live test happened
if it did not.

## Step 5 — Deliver

The SOP document, the list of defects found and fixed during testing, and any
steps that could not be verified and why.
